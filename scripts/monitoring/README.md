# Monitoring for the full-cohort Immuannot run

> Companion to [`BRIEF.md`](BRIEF.md) (the design doc this was built from). This README is the
> "how to actually deploy and use it" doc — read `BRIEF.md` first if you want the *why*.

## What's here

- **`heartbeat_receiver.py`** — runs on the Hetzner box (`hermes-agent`, 46.225.123.54). Stdlib-only
  HTTP server: accepts `POST /heartbeat`, appends to a JSONL log, serves the dashboard at `GET /`,
  and runs a background watchdog thread that fires an ntfy.sh push if heartbeats go stale or a
  heartbeat reports an anomaly.
- **`heartbeat_client.py`** — runs on the Workbench pipeline VM (or anywhere). Exposes
  `send_heartbeat(people_done, people_failed, people_total, current_disk_pct, current_mem_avail_pct)`
  for the future orchestrator to call every **~5 min** (revised 2026-08-04 from the original ~15
  min plan — see "Cadence" below), and a CLI for manual/synthetic testing.
- **This README.**

Nothing here touches the Hermes Agent project on the same box (different port, different systemd
unit, different directory — `~/hla-monitor/` vs `~/.hermes/`).

The dashboard is protected by **HTTP Basic Auth** (`MONITOR_DASHBOARD_USER`/`MONITOR_DASHBOARD_PASSWORD`, checked with `hmac.compare_digest`) — the browser's native login prompt blocks all page content until the password is entered. `POST /heartbeat` keeps its separate `X-Auth-Token` header, unrelated to the dashboard password. **Caveat, stated not hidden: this is plain HTTP, not HTTPS** — Basic Auth credentials and dashboard content travel unencrypted between browser and box. ## Deploy on the Hetzner box

**Status: already deployed and running as of 2026-08-03.** The steps below are the reproducible
record of what was done (useful if the box is ever rebuilt), not a to-do list — `hla-monitor.service`
is live on port 8943 right now. All commands run **on the Hetzner box** (`ssh root@46.225.123.54`,
confirm the prompt reads `root@hermes-agent` before pasting anything — see the Hermes project's own
lesson-learned about mixing up which terminal you're in).

### 1. Get the code onto the box

This repo (`pilot-validation`) is public on GitHub, so the intended path is a plain clone — keeps
future updates to a `git pull` rather than re-copying files by hand:

```bash
mkdir -p ~/hla-monitor
git clone https://github.com/marcserranos/pilot-validation.git ~/hla-monitor/repo
```

(If it's already cloned from an earlier session, `cd ~/hla-monitor/repo && git pull` instead.)

*What actually happened the first time:* the three monitoring files were built and locally tested
before being committed/pushed to GitHub, so the very first deploy used `scp` directly into
`~/hla-monitor/repo/scripts/monitoring/` instead of a clone. Once they landed in git (this same
session), `git pull` from `~/hla-monitor/repo` is the normal way to pick up any future change.

### 2. Add the firewall rule (Hetzner Cloud console or `hcloud` CLI)

**Add this rule to the existing `ssh-only` firewall — don't create a second, separate firewall
object.** A brand-new firewall created via "Create Firewall" is not automatically attached to
`hermes-agent`; it would need an extra "Apply to" step, and now you'd have two firewall objects to
keep track of for one server. Simpler: **Firewalls → click into `ssh-only` → Add rule**, then:

| Field | Value |
|---|---|
| Source | `Any IPv4` **and** `Any IPv6` (both toggled on — same as the existing SSH/ICMP rules) |
| Protocol | `TCP` |
| Port | `8943` |
| Port range | leave blank (single port, not a range) |
| Description | optional, e.g. `hla-monitor dashboard + heartbeat` |

This one rule covers both `GET /` (the password-gated dashboard) and `POST /heartbeat` (the
token-gated ingestion endpoint) — both live on the same port 8943, same process.

If you already had a separate "Create Firewall" screen open (as in the screenshot from this
session) with its own TCP 22 + ICMP rules pre-filled: that's fine too if you'd rather keep it
separate, just remember to also complete the **"Apply to"** step and select `hermes-agent`, or the
new firewall's rules never take effect. Either way, the values for the new rule are the same as
the table above.

Or via `hcloud` CLI if you have it installed and configured on your Mac (not the server):

```bash
hcloud firewall add-rule ssh-only --direction in --protocol tcp --port 8943 --source-ips 0.0.0.0/0 --source-ips ::/0
```

### 3. Create the env file (secrets — never committed)

On the box:

```bash
mkdir -p ~/hla-monitor
cat > ~/hla-monitor/.env <<'EOF'
MONITOR_PORT=8943
MONITOR_AUTH_TOKEN=<paste the openssl rand -hex 32 value you generated>
MONITOR_NTFY_TOPIC=<a fresh, unguessable string -- topic names on ntfy.sh are effectively public/guessable-secret, never commit the real one>
MONITOR_DASHBOARD_USER=hla
MONITOR_DASHBOARD_PASSWORD=<a mobile-typable random password -- alnum only is fine, no need for symbols>
MONITOR_LOG_PATH=/root/hla-monitor/heartbeats.jsonl
MONITOR_STALE_MINUTES=25
MONITOR_FAILURE_RATE_ANOMALY_PCT=15
MONITOR_DISK_DANGER_PCT=90
MONITOR_MEM_AVAIL_DANGER_PCT=10
EOF
chmod 600 ~/hla-monitor/.env
```

*What actually happened:* `MONITOR_DASHBOARD_PASSWORD` was generated directly on the box
(`python3 -c "import secrets,string; print(...)"`, 16 alphanumeric chars — phone-keyboard-friendly,
no `+/=` symbols) after Marc asked for the dashboard to be link-accessible-but-password-protected
instead of the original SSH-tunnel-only default. If you ever want to rotate it, generate a new
value the same way, update `.env`, then `systemctl restart hla-monitor`.

### 4. Install the systemd unit

```bash
cat > /etc/systemd/system/hla-monitor.service <<'EOF'
[Unit]
Description=HLA full-cohort pipeline heartbeat monitor
After=network.target

[Service]
Type=simple
EnvironmentFile=/root/hla-monitor/.env
ExecStart=/usr/bin/python3 /root/hla-monitor/repo/scripts/monitoring/heartbeat_receiver.py
Restart=on-failure
RestartSec=5
User=root

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now hla-monitor
systemctl status hla-monitor --no-pager
```

Confirm it's actually listening:

```bash
sudo ss -tlnp | grep 8943
```

### 5. View the dashboard

**Direct link (once the firewall rule from step 2 is in place):** open
`http://46.225.123.54:8943/` in any browser — phone, laptop, doesn't matter. The browser will show
a native login prompt (HTTP Basic Auth); enter username `hla` and the `MONITOR_DASHBOARD_PASSWORD`
from `.env`. Nothing on the page renders until that succeeds.

**SSH tunnel still works too**, if you'd rather not type the password on a given device, or before
the firewall rule is added:

```bash
ssh -L 8943:localhost:8943 root@46.225.123.54
```

Leave that running, then open `http://localhost:8943/` — you'll still hit the same Basic Auth
prompt either way, the tunnel just changes the network path, not the auth requirement.

## Test end-to-end with synthetic heartbeats (before the real orchestrator exists)

From **any machine with outbound internet** (your Mac, the Workbench VM once it exists, or the
Hetzner box itself against its own public IP) — this exercises the real deployed receiver, not a
local mock:

```bash
python3 heartbeat_client.py \
  --url http://46.225.123.54:8943 \
  --token <the same MONITOR_AUTH_TOKEN from the .env file> \
  --people-total 100 --disk-pct 20 --mem-avail-pct 70 \
  --simulate 10 --simulate-interval-sec 10
```

This ramps a fake `people_done` from 0 → 100 over 10 heartbeats, ~10s apart. Watch the dashboard
update live. To also test anomaly alerting, add `--simulate-fail-at 6` — it injects a failure
spike starting at step 6, which should flip the dashboard to the `ANOMALY` state and (if you've
subscribed to the topic in `.env` in the ntfy app) push a notification. To test the *stale*
alert, just stop sending heartbeats (kill the simulate early or don't run it) and wait >25 min —
you'll get a separate "no heartbeat in NN min" push.

**Before the real run**, subscribe to the ntfy topic so pushes actually reach you: install the
ntfy app (iOS/Android) or open `https://ntfy.sh/<your topic>` in a browser, and subscribe
to the topic name from `~/hla-monitor/.env` on the box (no server URL needed, defaults to ntfy.sh).

This was verified locally (loopback, not the deployed box) during development: a 6-step simulate
run with a failure spike at step 4 correctly flipped `anomaly: true` at the right step, the
dashboard rendered the ANOMALY banner and progress chart, and both a bad and a missing
`X-Auth-Token` were correctly rejected with `401`.

## Rolling failure rate — how it's actually computed

`BRIEF.md` proposed "rolling failure rate over the last ~50 people." The real orchestrator (not
built yet) only reports **cumulative** `people_done`/`people_failed` counts each call, not a full
per-person outcome log — so a literal "last 50 people" window isn't available to compute from.
Instead, `heartbeat_client.py` keeps a tiny local state file (`client_state.json`, gitignored) of
the previous call's cumulative counts, and computes the failure rate **among people completed
since the last heartbeat** (i.e. a time-windowed proxy, naturally scoped to roughly one cadence
interval rather than a fixed people-count). At the ~5-min cadence below and the production
24-worker config, that window naturally captures on the order of ~20-25 people per interval — a
reasonable sample size, not too noisy. This is documented here rather than silently diverging from
the brief's wording. If a true fixed-N rolling window ever matters more than this approximation,
the orchestrator would need to report a per-person outcome log instead of just cumulative counts —
not needed for the current anomaly-detection use case.

## Cadence: revised again to 2 minutes (2026-08-05)

Marc, before the real launch: he wants tighter feedback specifically for the first watched minutes
of the run, when he's checking that everything actually works before going to sleep. Overhead is
negligible at any of these intervals (the reasoning in the ~5-min section below still holds
verbatim — a few in-memory counters and one small POST), so the only real cost of going from 5 min
to 2 min is a slightly denser JSONL, and the benefit is real: on a ~$3.55/h VM, faster confirmation
that the pipeline is alive is worth more than a marginally smaller log. **`MONITOR_STALE_MINUTES`
moved 15 → 6** to keep the same ~3x-cadence slack ratio (one dropped beat is not an alarm; three
missed in a row is).

Two lifecycle additions landed alongside this, both aimed at "close the laptop and sleep safely":

- **A startup heartbeat**, sent before any long work begins. Without it, an orchestrator that died
  early (bad flag, missing cohort file, crash on person 1) produced *total silence*: the dashboard
  sat on `WAITING`, and the stale watchdog never armed, because it skips while `last_received_ts`
  is `None`. Now there is always at least one beat, the watchdog is armed from second one, and the
  dashboard flipping to `STARTING` is instant proof the VM can reach this box.
- **`run_state`** (`starting` / `running` / `complete` / `failed`) plus `phase`. Previously, a run
  that *finished successfully* was indistinguishable from one that *crashed* — heartbeats simply
  stopped in both cases, and the watchdog fired the same 🚨 "no heartbeat in N min" push at 3am.
  The receiver now pushes a ✅ completion notice, shows `COMPLETE`, and stops arming the stale
  alarm. A Ctrl-C or an unhandled exception sends `failed` on the way out, so that's unambiguous too.

## Cadence: the earlier revision to ~5 minutes (2026-08-04, was ~15 min in the original BRIEF.md plan)

Reasoning (Marc's question, answered directly): heartbeat overhead is negligible at any interval
from 1 minute to 45 — it's a few in-memory counters and one small HTTP POST, nothing a 96-core VM
or this small Hetzner box would notice. The real trade-off is stall-detection latency vs. noise.
**5 minutes** is the sweet spot: meaningfully faster stall detection than 15 min (every minute a
real stall goes unnoticed on a ~$3/hr VM is money spent producing nothing — this project had a
real, hours-long stall incident this session), while going shorter than ~5 min stops buying
anything, since human reaction time becomes the actual bottleneck, not detection time. **The
watchdog's stale threshold should move from the original 25 min to ~12-15 min** (2-3x the new
cadence, same slack ratio as before) — update `MONITOR_STALE_MINUTES` in `~/hla-monitor/.env` on
the Hetzner box and restart the service (`systemctl restart hla-monitor`) to apply; not yet done as
of 2026-08-04, since the orchestrator that would actually use this cadence doesn't exist yet.
**One hard requirement carried from this session's own incidents: the orchestrator must compute
`people_done`/`people_failed`/etc. from in-memory counters it already tracks, never by re-scanning
the output directory** — a broad filesystem scan on every heartbeat would reintroduce the exact
`du`/`df`-hanging failure mode this project spent a full day/night diagnosing (ENVIRONMENT.md
quirk #25).

## Wiring into the real orchestrator (later, small step)

Once the production orchestrator exists, it just needs to call, every ~5 minutes:

```python
from heartbeat_client import send_heartbeat

send_heartbeat(
    people_done, people_failed, people_total,
    current_disk_pct, current_mem_avail_pct,
    receiver_url="http://46.225.123.54:8943",
    auth_token=os.environ["MONITOR_AUTH_TOKEN"],  # set in the Workbench VM's own env, not hardcoded
    vm_hourly_rate_usd=<picked once the production VM size is chosen>,
    budget_usd=300,
)
```

Or, per `BRIEF.md`'s alternate shape: have the orchestrator write its own `progress.json` snapshot
on its own schedule, and a separate tiny cron/loop on the Workbench VM reads that file and calls
`send_heartbeat()` — either shape works with the receiver/client as built; no redesign needed
either way.

## Known limitations (by design — minimal on purpose)

- Dashboard auth is HTTP Basic Auth over **plain HTTP, not HTTPS** — adequate for a low-sensitivity,
  aggregate-only operational dashboard, not for anything more sensitive. See open decision #7 above
  for the optional HTTPS-via-Caddy upgrade path if this ever needs to change.
- No historical analytics beyond the last 500 heartbeats' chart — this is a liveness/sanity
  dashboard, not a results-analysis tool.
- `cost_so_far_usd` is `null` until a VM hourly rate is supplied (open decision #6).
- Single receiver process, no HA — acceptable for a personal monitoring tool watching one run.
