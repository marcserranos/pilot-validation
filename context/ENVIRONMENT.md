## Repo & VM layout

- **Workbench VM** `HLAcalling_pilot_v0_m` (Standard, 4 vCPU / 25 GB RAM / 88 GB disk, Ubuntu 24.04, us-central1-a):
  - `~/repos/pilot-validation` — this repo (manually `git clone`d; auto-clone never worked — quirk #3).
  - `~/tools/SpecHLA` — upstream, built via `bash index.sh` in `pixi shell -e spechla`. Has one local source patch not in git (see Fixes).
  - `~/tools/SpecImmune` — upstream; HLA reference db built locally (see Fixes).
  - `~/ref/Homo_sapiens_assembly38.fasta` (+ `.fai`, `.dict`) — hg38 reference, downloaded once (~3 GB) because remote `-T gs://…` doesn't work (quirk #11).

  - `~/mnt/aou-controlled` — gcsfuse mount of the genomics bucket (quirk #11).
  - `~/pipeline_outputs/<person_id>/` — all pipeline outputs (quirk #12).
  - Two pixi envs (`spechla`, `specimmune`) in one `pixi.toml`; activate with `pixi shell -e <name>` **from inside `~/repos/pilot-validation`** (quirk #1).

## Pipeline runbook (one person, end to end)

Prereqs: gcsfuse mount active (quirk #11), reference at `~/ref/`, both pixi envs built.

```bash
# 0. Mount the bucket if not already (quirk #11)
mkdir -p ~/mnt/aou-controlled
gcsfuse --billing-project wb-glacial-potato-8710 --implicit-dirs vwb-aou-datasets-controlled ~/mnt/aou-controlled

# 1. Slice both technologies to the chr6 HLA region + convert to FASTQ (samtools lives in the spechla env)
cd ~/repos/pilot-validation && pixi shell -e spechla
bash scripts/slice_and_fastq.sh <id> <cram_path_rel_to_mount> <lr_bam_path_rel_to_mount>
#   paths e.g.:  pooled/wgs/cram/v8_base/wgs_<id>.cram
#                pooled/longreads/v8_delta/BI/revio/bam/<id>/GRCh38/<id>.bam

# 2. SpecHLA (short-read) — from ~/tools/SpecHLA, spechla env
{ time bash script/whole/SpecHLA.sh -n <id> \
    -1 ~/pipeline_outputs/<id>/R1.fastq.gz -2 ~/pipeline_outputs/<id>/R2.fastq.gz \
    -o ~/pipeline_outputs/<id>/spechla_output/ ; } 2> ~/pipeline_outputs/<id>/spechla_timing.txt

# 3. SpecImmune (long-read) — from ~/tools/SpecImmune, specimmune env
#    bwa config (proven; see DECISIONS re: minimap2) + visualization disabled (cosmetic, missing converter)
{ time python3 scripts/main.py -n <id> -o ~/pipeline_outputs/<id>/specimmune_output/ \
    -j 4 -y pacbio-hifi -i HLA -r ~/pipeline_outputs/<id>/LR.fastq --db ./db --visualization "" ; } \
    2> ~/pipeline_outputs/<id>/specimmune_timing.txt

# 4. 3-way comparison table (writes ~/pipeline_outputs/<id>/comparison.md; paste that back to fold into .local.md)
python3 ~/repos/pilot-validation/scripts/compare_hla_results.py <id>
```

Region window: **`chr6:29,500,000-33,500,000`** (4 Mb — classical MHC + ~440 kb pad each side). See DECISIONS / EXPERIMENTS for the open padding-narrowing experiment.

> Note: `slice_and_fastq.sh`'s *printed* SpecImmune hint omits `--visualization ""`; use the runbook form above — disabling it is the standing decision (DECISIONS). All project scripts referenced throughout this file live in `scripts/`; only upstream tools' own internal paths (`~/tools/SpecHLA/script/...`, `~/tools/SpecImmune/scripts/...`) are unaffected by this repo's layout.

## Workbench quirks & gotchas — read before doing anything new

1. **`pixi shell` only works from the manifest's directory.** `cd ~/repos/pilot-validation` first, always. Elsewhere it fails silently into a *plain, non-activated* shell (no error) and every tool command then breaks with confusing "command not found". Check for the `(omni-hla-pilot:<env>)` prompt prefix before trusting the shell.
2. **`pixi shell` sometimes misses its 3-second hook window.** It prints a fallback line like `. /tmp/pixi_env_XXX.sh` — run that line manually to finish activation. **Corollary:** any commands pasted in the *same block* as the `pixi shell` line get swallowed during this hiccup — paste run commands *separately*, only after the `(omni-hla-pilot:<env>)` prompt appears.
3. **Workbench's "Add repository" auto-clone never worked** this project — registering the repo, restarting the app, making it public: none cloned it into `~/repos/`. Don't debug it; just `git clone` manually.
4. **`Failed to get AoU version: no AoU resources in workspace`** prints on every fresh shell — benign noise, unrelated to data access (a real BigQuery query against the CDR returns real rows despite it).
5. **The CDR is not exposed via shell env vars** (`env | grep -i cdr` → nothing). It lives in a separate GCP project (`wb-silky-artichoke-2408`, dataset `C2025Q4R6`) and is accessed via BigQuery with a fully-qualified table path — the Cohort/Dataset Builder auto-generates this in exported notebook snippets (the intended access pattern).
6. **No sudo** (`jupyter` user not in sudoers) — can't apt-install anything. Work around missing system tools rather than installing (see the `less` fix).
7. **samtools in the `spechla` env (v1.21) has built-in GCS support** (`gs+http`/`gs+https`/`gs` handlers) — but it does **not** cleanly handle this requester-pays bucket (quirk #11); use the gcsfuse mount instead.
8. **Two collaborators, siloed apps, no conflict.** Aleix (`aleixruf@researchallofus.org`) works in his own app instance in the same workspace. Check his `hla-pilot-cohort-snapshot` resource before redoing the stratified ~100-person selection — it may already exist.
9. **Always confirm you're reading the current CDR release, not an archived one.** AoU republishes core docs per CDR version and keeps old ones live, marked "(Archived …)". Confirmed 2026-07-08: **v9 (`C2025Q4R6`) is current.** Re-check the "Current CDRs" table before trusting any cited fact from an older session.
10. **The platform migrated** from the original AoU Researcher Workbench (Terra/Firecloud) to **Verily Workbench** — visible in the `vwb-` vs legacy `fc-` bucket split and UI differences. Any doc/tutorial/memory using old-platform terminology needs live re-verification; when something doesn't match the screen, suspect staleness first, not user error.
11. **Don't use raw `gs://` URLs with samtools/htslib against the genomics bucket — use a `gcsfuse` mount.** htslib doesn't reliably attach billing to requests against this requester-pays bucket (`GCS_OAUTH_TOKEN` alone → `Invalid argument`; adding `GCS_REQUESTER_PAYS_PROJECT` → `Operation not permitted`; neither works). The confirmed working method:
    ```bash
    mkdir -p ~/mnt/aou-controlled
    gcsfuse --billing-project wb-glacial-potato-8710 --implicit-dirs vwb-aou-datasets-controlled ~/mnt/aou-controlled
    ```
    **`--implicit-dirs` is not optional** — without it nested paths silently don't resolve (`ls` looks empty) because GCS has no real directories and this bucket has no directory-placeholder objects. This gcsfuse (v3.10.0, preinstalled) daemonizes automatically — no second terminal. Then `~/mnt/aou-controlled/…/<file>.cram` works with plain `samtools view`. **When debugging remote/mount access, always redirect output to a file and check `$?` — never pipe through `tail`/`grep` while diagnosing; a filtered pipe once silently hid a real error behind stale-looking success output.** Public buckets (e.g. the Broad reference bucket) don't have this problem — plain `gs://` works for those.
12. **Pipeline outputs live under `~/pipeline_outputs/<person_id>/`, not `/tmp`.** `/tmp` isn't visible in the Jupyter file browser (confined to `$HOME`) and reads as disposable; `~/pipeline_outputs/` is the same persistent disk, just visible.
13. **To find a person's real long-read BAM, verify file existence directly — never infer it from a path pattern, column name, or the `has_lr_whole_genome_variant` BigQuery flag.** `v9/wgs/long_read/manifest.tsv` has 15,424 rows / 14,521 unique people across 5 platform labels (revio 11,070, ont-r10.4.1 2,020, sequel2e 1,219, sequel2 991, ont-r9.4.1 124). The durable rules, learned the hard way (full saga in git history — this quirk was ~110 lines before the 2026-07-22 cleanup):
    - **Check `os.path.exists()` against the mount** for both known BAM-holding columns (`grch38_bam`, then `grch38_haplotagged_bam`), per row. AoU publishes each release batch differently (assembly-based vs. alignment-based products, inconsistent column names across platforms, release-folder names we don't know in advance) — any path/folder pattern inferred from a handful of confirmed cases is a hypothesis about the dataset, not a property of it. Existence-checking is immune to all of it. `build_experiment_d_cohort.py`'s `find_existing_bam()` implements exactly this (prefers the raw `grch38_bam`); it's slower (~2×15,424 mount stats, a few min per cohort build) but correct by construction.
    - **Resolve per row, then dedupe to any resolving row per person.** ~879 of 14,521 people have >1 manifest row (different center/platform combos); a person's newest row can be a dead end while an older row resolves fine. Filtering by platform label alone silently drops people who have a working row under a different label.
    - **`v9_delta`-rooted `pacbio`/`ont` rows** resolve to a de novo phased assembly + variant-call product with no aligned BAM — a different data product, not a missing file; existence-checking excludes them correctly without needing to know that in advance.
    - **General debugging lesson from the saga:** print/read actual values before trusting a computed boolean mask (a silent `&`-vs-`==` operator-precedence bug once produced garbage that looked like a real result), and don't trust an unverified arithmetic claim as if checked.
    - **Current state (2026-07-21): every one of the 14,521 people now has a real `grch38_bam`.** AoU backfilled the previously-missing revio BAMs between 07-11 and 07-21, obsoleting the earlier "2,763-person floor." Confirmed by re-checking this quirk's own previously-dangling case (person 1008366) — now resolves as real. See `reports/lr_data_census/README.md` and DECISIONS.md (Resolved). The existence-check discipline above still stands regardless — it's how you'd catch the *next* shift, in either direction.
14. **The VM auto-stops after ~1 hour with no process running** — not "1 hour of inactivity" loosely. Correction (Marc, 2026-07-21): a long foreground job keeps the VM up for its full duration; the idle clock only starts once the process exits. So "job finishes, VM stops an hour later and wipes the terminal" is a distinct failure mode from "VM kills a running job" — it does *not* do the latter (see quirk #22, which originally misdiagnosed this). Either way: **assume the VM and its terminal sessions have been restarted at the start of every session.** A large fraction of session-start errors trace to this:
    - **The gcsfuse mount does not survive a stop/restart** — it's gone every new session. Remount (quirk #11) *before* anything that reads bucket data. A start-of-session `FileNotFoundError` on `~/mnt/aou-controlled/…` almost always means "the VM slept, remount," not a real path problem.
    - **After remounting, the FUSE layer needs a beat to become ready.** gcsfuse prints `File system has been successfully mounted` but a command fired in the *same paste* can still race ahead and get `FileNotFoundError`. Run the mount on its own, then **verify with `ls` of a known path** (which also warms the implicit-dir metadata cache) before running dependent commands — don't chain the mount and the consumer in one paste (same lesson as quirk #2).
    - **Running processes and `/tmp` don't survive; the persistent home disk does.** `~/pipeline_outputs/`, `~/repos/`, `~/tools/`, `~/ref/` all survive the restart fine — only the mount, background processes, and the activated pixi shell need redoing.
    - **Reconfirmed on the new n2-highcpu-32 test VM, 2026-08-03 (Marc): the causal direction is strict.** If the console/session shows the VM has restarted, whatever was running *must* have already exited first — the idle-after-exit clock is the only path to a restart, there is no separate "VM kills a running job" mode (see the correction above). **Practical implication when you come back to a restarted VM after an unattended run and find thin/empty results: do not assume the run was interrupted mid-way — assume it ran to completion (or crashed) and produced that thin/empty output *while still running*, then sat idle for an hour, then restarted.** Diagnose it as "why did a completed/crashed run produce nothing," not "was it cut off partway." Concretely bit this project's own history: an empty `core_scaling_experiment.tsv` after a restart was initially (wrongly) suspected to be an interrupted-mid-sweep artifact — the real, still-unresolved-as-of-this-note possibilities are (a) a real logic bug in the script that lets it reach completion without writing rows, or (b) the unattended script was running directly in a plain terminal (no `tmux`/`nohup`) and a dropped browser/SSH session sent it a `SIGHUP`, killing the entire foreground pipeline near-instantly — which *also* satisfies "the VM only restarts after something running has exited" without requiring any bug in the pipeline logic itself, and is indistinguishable from (a) purely by inspecting the final output files. **Standing practice from now on for any unattended run expected to take more than a few minutes: always launch it inside `tmux` (or `nohup ... & disown`) AND `tee` its full stdout/stderr to a persistent log file** — not just let the data-bearing output files be the only record. Never trust "the VM looks idle/restarted, so the run must be done" as confirmation of success; the persistent log is what actually proves how far it got.
16. **Check `reference/` before any external research (web fetch, search, browser) for AoU documentation.** The 59-page "How the All of Us Genomic Data are Organized v9.pdf" is saved there, and `reference/AOU_DATA_ACCESS_NOTES.md` logs what's already been extracted from it (bucket paths, schemas, confidence markers). Confirmed 2026-07-10: the genetic-ancestry TSV's location/schema was re-derived from scratch via web search + browser automation (including a blocked 403 and manually paging the PDF in Chrome) when `AOU_DATA_ACCESS_NOTES.md` §6 already had the schema and the local PDF had the rest — a `grep` + `Read` would have taken seconds. **Standard practice: `grep`/read `reference/AOU_DATA_ACCESS_NOTES.md` and check for a matching local doc first; only go external if it's not covered.**
17. **SpecImmune must always run inside the `specimmune` pixi env — never assume the ambient shell's env doesn't matter.** Its long-read pipeline shells out to `sniffles` (SV caller), which is only on `PATH` inside `specimmune`, not `spechla` (which has `samtools` but not SpecImmune's own deps). Running `python3 scripts/main.py` from a `spechla`-activated shell fails deep inside the pipeline (`sniffles: command not found`) on every gene, cascading into missing-VCF errors — **but `main.py` still exits 0**, so a naive `$?` check reports success while producing zero real output. Confirmed 2026-07-09: an entire unattended 9-config sweep silently produced only NA rows this way. **Fix, now standard practice: invoke SpecImmune via `pixi run --manifest-path ~/repos/pilot-validation/pixi.toml -e specimmune -- python3 scripts/main.py ...`** instead of relying on `cd`-and-hope — this pins the environment regardless of what shell launched the script. **Also: after any automated SpecImmune call, verify the actual expected output file exists — never trust exit code alone** (`run_aligner_pad_sweep.sh` does both now).

18. **SpecHLA can silently return mostly-empty per-gene results while exiting 0 and writing a real `hla.result.txt`.** Confirmed 2026-07-10: a genuinely starved input (gene-cluster window truncated to 100-5000bp, well below what's needed) made SpecHLA finish in 22-62 seconds — 4-11x faster than the ~4m14s floor seen with adequate data — because it appears to skip/abort per-gene processing when a gene has too few reads, rather than erroring out. The result file still existed and passed the standard "does the expected output file exist" check used elsewhere in this project, even though most of its 8 genes were blank (`-`). **Fix: any automated SpecHLA sweep must also check per-gene completeness (count non-`-` genes in `hla.result.txt`, or its line count), not just file existence** — same category of lesson as quirk #17 (SpecImmune/sniffles: exit 0 ≠ actually worked), a different failure mode, same rule: a coarse success signal (exit code, file existence) is not sufficient on its own for either tool.

19. **The pipeline generates ~3 GB of intermediates per person (almost all from SpecImmune) — with no cleanup, the ~138 GB disk fills at ~person 10 and every later person fails instantly with `No space left on device`.** Confirmed 2026-07-11: an unattended Experiment D run completed 10 people, then person 11's SpecImmune wrote partial output as the disk hit 100%, and persons 12-60 all failed at pixi env activation (`/tmp` is on the same full overlay). The failures are clean/retryable (resumable design), but the run is dead until space is freed. **Disk policy, now enforced:** the only must-keep outputs are tiny (`comparison_log.csv`, tool result files `hla.result.txt`/`*.formatted.txt`, `*_timing.txt` — all <1 MB); everything bulky (sliced BAMs, FASTQs, tool alignment/assembly intermediates) is regenerable or redundant once the calls are in `comparison_log.csv`. Rule: **inside a person dir, anything >1 MB is disposable.** `run_experiment_d.sh` now auto-prunes each person the moment they're marked done (drops it from ~3 GB to a few KB, keeping disk flat across the whole cohort); `prune_pipeline_outputs.sh` applies the same policy on demand (`--dry-run` to preview) for cleaning old closed-experiment cruft. We never persist raw CRAM/BAM (streamed from the mount) and no longer persist the sliced versions either (re-slicing costs ~5 s).

20. **`bash`'s `>` redirect needs the target directory to already exist** — `cmd > ~/newdir/out.txt` fails with `No such file or directory` if `~/newdir` doesn't exist yet, even if the script itself would `os.makedirs()` it internally — bash resolves the redirect target before the command ever runs. Always `mkdir -p` the output directory first, as its own step, before any redirected command.
21. **IPD-IMGT/HLA's `Allelelist_history.txt` encodes each release version as a plain digit string, not `X.Y.Z`** — e.g. `3650` = release 3.65.0, `3380` = 3.38.0, and the single oldest column `116` = 1.16.0 (pre-dates the patch-number convention, patch assumed 0). Decode rule: last digit = patch, preceding 2 digits = minor, remainder = major. Confirmed correct by cross-checking against two independently-known versions already in this project (SpecHLA's DB 3.38.0, SpecImmune's DB 3.64.0 — both decoded correctly). See `experiment_a3_allele_space_coverage.py`'s `decode_version()`.
22. **A script that only prints its output (never writes to disk incrementally) can lose that output to terminal/session loss even when the process completes — a different, easier-to-hit failure mode than "the VM killed the job."** Real incident, 2026-07-21, `lr_manifest_format_census.py` v1: it did all its existence-checking (16 columns × ~15,424 rows) but only wrote a file in the last lines of `main()`, printing its distribution tables to stderr otherwise. Two independent, compounding root causes destroyed the ~5h result: **(a)** the run finished and printed everything to the terminal, then the VM sat idle an hour and stopped, wiping the scrollback (no tmux/screen/redirection to survive it) — first misdiagnosed as a mid-run VM kill, but the VM doesn't stop mid-job (quirk #14); **(b)** separately, `--sample-only` and the real full-run mode wrote to the *same* default output path, so a later `--sample-only 50` sanity check (per the multi-agent workflow — DECISIONS.md/STATUS.md on concurrent editing) silently overwrote the real ~14,521-row result with 50 rows. **Fixes, now standard for any job past a few minutes:** **(a)** write output to disk incrementally — process in chunks (a few hundred rows), append+fsync each to a checkpoint, make reruns resume from the last completed chunk (finer-grained mirror of `run_experiment_d.sh`'s per-person resumability); **(b)** never share an output path between a test mode and a real mode (`--sample-only` now gets its own path unconditionally). Also parallelized the checks (`ThreadPoolExecutor` — FUSE-I/O-bound, not CPU-bound, so threading helps despite the GIL) and dropped companion/index files (`.bai`/`.tbi`/`.csi`/`.pbi`/`.gzi`) from the checked set — near-certain to exist with their primary, and were ~doubling the check count for no new information.

23. **Two concurrent invocations of a per-person orchestrator (e.g. `run_core_scaling_experiment.sh`, and this generalizes to any future production orchestrator) will silently corrupt each other's shared per-person intermediate files, even when the *final* results files are safely isolated per-invocation.** Real incident, 2026-08-03: the `--out-suffix` mechanism (quirk fix in `run_immuannot_person.py`, 2026-08-02) isolates the *final* `immuannot_calls*.tsv`/`immuannot_timing*.tsv` files between concurrent workers — but it does **not** isolate the *intermediate working directory* (`~/pipeline_outputs/<person_id>/immuannot_output/`, holding the trimmed FASTA and `.gtf.gz` outputs), because that path is keyed only by `person_id`, not by invocation. When a second (and eventually third) full instance of `run_core_scaling_experiment.sh` got launched against the same person_ids — apparently from the launch command being re-run/re-pasted during troubleshooting, cause never fully confirmed — one instance ended up with zero child processes and zero output for 45+ minutes, most plausibly because a later instance rewrote the trimmed FASTA / `.gtf.gz` out from under the first one mid-read. Diagnosed via `ps -ef --forest`, comparing two snapshots ~20s apart: the stalled instance had no children at all (not "slow," genuinely stuck), while a `[bash] <defunct>`/`[sleep] <defunct>` zombie pair revealed an earlier duplicate that had already silently died. **Fix, now standard for any orchestrator expected to run more than a few minutes unattended: a PID-file lock at startup** (`run_core_scaling_experiment.sh` now does this — checks `$OUTROOT/*.lock`, refuses to start with a clear error if a live PID is already holding it, cleans up a stale lock from a dead PID, and removes its own lock via an `EXIT` trap on any termination path). A second launch now fails loudly and immediately instead of quietly corrupting shared state. **This same lock pattern must be built into the eventual full-cohort production orchestrator** (not yet written) — the failure mode generalizes to any script that writes to a per-person directory keyed only by `person_id`.
24. **`ps -ef --forest` combined with two snapshots ~15-30s apart is the fast, reliable way to distinguish "genuinely stuck" from "just slow."** If the process tree under the orchestrator's PID shows different child PIDs (or growing `TIME`) between the two snapshots, it's real progress; if it's identical with no children at all, it's stuck. Faster and more conclusive than staring at a quiet log file guessing whether "no new output in N minutes" means trouble.

25. **`du -sm <dir>` on this project's disk-usage checks can stall for tens of minutes on this VM once the target directory has accumulated real data, and gets worse over time.** Real incident, 2026-08-03: `run_core_scaling_experiment.sh`'s disk check called `du -sm ~/pipeline_outputs` (a full recursive tree walk) before and after every config — two separate ~15-49 minute stalls, both immediately before the `xargs` launch line, were misdiagnosed at first as hung/duplicate processes before the real cause (the disk check itself, not anything downstream) was found.
    - **CORRECTION, same day: the first fix (switching to `df -m --output=used <dir>`) was wrong — it is NOT actually faster/safer here, it just failed differently.** Re-tested in a clean, watched, foreground, single-process run (no duplicates, no session loss, nothing else that had previously muddied the diagnosis) and the `df`-based version stalled for **2+ hours** at the exact same point. This VM has two `gcsfuse` FUSE mounts active; the working hypothesis is that both a large/growing-tree `du` and a whole-filesystem `df` are vulnerable to hanging system-wide when even one mounted filesystem (including an unrelated FUSE mount) is slow to respond — `df`'s "O(1), just reads a counter" reputation does not hold up when the query can end up touching the whole mount table. **The real, confirmed-reliable pattern across this entire incident, without a single exception: `du -sm` scoped to one small, specific directory** (Phase 0's `person_dir` check, `~/pipeline_outputs/<person_id>/immuannot_output/`, never once stalled, run after run). **Fix, actually correct this time: scope every disk check to the specific small directories relevant to that check (e.g. sum `du -sm` over just the current batch's person_ids), never the whole `$OUTROOT` tree and never a whole-filesystem `df`.** Added `timeout 5` per directory as a hard safety net regardless of the theory being right. **Lesson beyond the specific fix: when a "should be instant" system command mysteriously hangs, don't assume a different flag/command in the same broad-scope family solves it — the FIRST fix here looked identical in spirit to the bug it was fixing (both are "ask the OS about a large scope, once, and trust it's fast"). Narrowing scope, not swapping which whole-scope command you use, was the actual fix.** Apply the narrow-scope pattern in the eventual production orchestrator — a broad disk check against thousands of people's accumulated output would be catastrophic at that scale, not just annoying.

26. **"Remember to remount and verify before launching" is not a reliable enough discipline for an unattended/overnight script — it failed multiple times in one session, for both the human and the assistant giving instructions.** Real incident, 2026-08-03/04: after hours of chasing what looked like exotic hangs (duplicate processes, `du`/`df` behavior, disk scope), the actual cause of at least one full overnight failure was much simpler — the VM had restarted (dropping the mount, per quirk #11/#14) between a remount and the next launch, `run_core_scaling_experiment.sh` had no check for this, and — critically — since the script has no `set -e`, a Phase 0 that `FATAL`'d instantly on a missing manifest did NOT stop the script; it silently continued into Phase 1 and got stuck there for hours with no indication the real problem was upstream. **Fix: any script that depends on the mount should hard-check for it as its very first action and refuse to start at all if it's missing** (`run_core_scaling_experiment.sh` now does this) — don't rely on a human or an assistant remembering to check first, especially for anything meant to run unattended for a long time. **Apply this same up-front hard check in the production orchestrator.**

## Package management

Deps for SpecHLA and SpecImmune are managed with [pixi](https://pixi.sh), not conda — two separate pixi envs (`spechla`, `specimmune`) in one `pixi.toml`, mirroring how upstream ships them as two never-designed-to-coexist conda envs. Deps are loosely pinned rather than a full port of upstream's exact-pin `environment.yml` (SpecHLA's own `CONDA_PACKAGING_PROPOSAL.md` calls its pins outdated/overly strict; SpecImmune's has 400+ auto-exported pins not worth hand-porting). SpecHLA itself isn't conda-packageable — it vendors pre-compiled binaries (`bin/bcftools`, `bin/novoalign`, `bin/fermikit/`) called by hardcoded relative path, so pixi supplies only the surrounding toolchain; the tool is cloned from source and built via `bash index.sh`.
