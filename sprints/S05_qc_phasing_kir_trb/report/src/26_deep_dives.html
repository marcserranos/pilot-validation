Deep divesThe raw data, file by file

The background course gives the ideas. These three modules go one level down: which files exist, what one line of each looks like, and the exact steps that turn them into a coverage number, a "same contig" statement and an expression value. The example lines are made up for illustration (fake names and coordinates) but have the real layout.

Where the data lives and how we reach it

All participant-level data stays inside the All of Us Researcher Workbench, a Google Cloud environment. Our analyses run on one virtual machine there (called big_run: 4 CPUs, 32 GB of memory, $0.37 per hour). The VM has the controlled-tier data bucket mounted as a folder, read-only:

~/workspace/vwb-aou-datasets-controlled-v9/v9/
  wgs/long_read/manifest.tsv        one row per long-read person, 61 columns of file paths
  wgs/long_read/...                 the files those paths point to (BAMs, assemblies, alignments)
  multiomics/rnaseq/manifest.tsv    one row per RNA-seq sample (8,980), BAM paths
  multiomics/rnaseq/rnaseq_metadata.tsv
  multiomics/rnaseq/rnaseqc2/       gene TPM matrix, QC metrics
  multiomics/rnaseq/rsem/           RSEM gene and transcript expression

The manifest is the index. For long reads, the columns used here are:

  • grch38_bam: the person's HiFi reads aligned to the reference genome (GRCh38, no alternative contigs).
  • assembly_hap1_fa, assembly_hap2_fa: the person's two haplotype assemblies (FASTA, gzip).
  • assembly_hap1_aln2_hg38_paf (and hap2): where each assembled contig lands on the reference (PAF).

Our own pipeline then adds files under ~/pipeline_outputs/ on the VM: the HLA and KIR annotations (GTF) per person and haplotype, and "Table 1" (hla_calls_rich.tsv), which collects every HLA call. Every S05 script reads these, writes per-person INTERNAL tables under ~/s05/internal/ (never copied out) and aggregate PUBLIC tables under ~/s05/results/, which are masked and then committed to the repo.

Two practical limits shape the work. Files are read through a network mount, so a script that reads 12,000 BAMs is limited by I/O, not by CPU. And the VM stops itself after about an hour idle, so long jobs are written to resume from a checkpoint.

How we know the coverage of a region

The file. Coverage comes from the person's aligned reads, the BAM file (grch38_bam). A BAM is a compressed table with one record per read. The fields that matter here:

read name           flag  chrom  start      MAPQ  CIGAR            sequence ...
m84011_..._/1234    0     chr6   32601120   60    18234M2I3011M    ACGT...   (one ~21 kb HiFi read)
m84011_..._/5678    16    chr6   32598877   0     15002M           ACGT...   (MAPQ 0: fits two places)
  • start + CIGAR say which reference bases the read covers (18234M = 18,234 aligned bases, 2I = 2 extra bases in the read).
  • MAPQ is the aligner's confidence in the placement, 0 to 60 (background).

The measurement (script 58):

  1. A BED file lists 137 regions: five 2 Mb control windows on chr2, 3, 5, 10 and 12, the MHC window (chr6:29.5–33.5 Mb), the KIR window on chr19, the TRB window on chr7, and every HLA, KIR and TRB gene (GENCODE v46 coordinates).
  2. samtools bedcov walks each region and adds up, base by base, how many reads cover it. That sum divided by the region length is the mean depth. It runs twice: once counting every read (MAPQ ≥ 0) and once only confidently placed reads (MAPQ ≥ 20).
  3. The person's control depth is the median of the five control-window means. Relative depth = region depth / control depth. It cancels how much DNA the person was sequenced with, so people are comparable.
  4. For comparisons between people, 59 and 67 also use normalised depth: relative depth divided by the cohort median for that region and platform. 1.0 means "as covered as a typical person on the same machine".

A worked example. If a person's HLA-DQB1 region (about 7 kb) has a summed depth of 105,000, the mean depth is 15×. If their control depth (the median of the five control windows) is 18×, relative depth is 15 / 18 = 0.83, which is about the cohort's typical value for the MHC (median 0.83). The MHC reads a bit below 1.0 for nearly everyone, not because of a deletion. The likely reason (not tested) is that reads from haplotypes very different from the reference align less completely there.

What "coverage" cannot tell you. It counts reads, not which parent they came from, and it is averaged over a region, so a small dip inside a gene is diluted. Low MAPQ in paralogous genes (KIR, some HLA pseudogenes) means reads are counted at q0 but may belong to a neighbour. The per-person table is ~/s05/internal/58/per_person_depth.tsv (person × region × MAPQ: mean depth, read count, control depth, relative depth).

How we know two genes are on the same contig, and what it means

Step 1, the assembly. hifiasm overlaps each person's reads and outputs two FASTA files, one per haplotype. A FASTA is a header line and then the sequence:

>h1tg000012l
GATTACAGGCT...   (1.8 million bases: one contig = one continuous piece of assembled DNA)
>h1tg000013l
...

A contig is continuous by construction: every base of it is backed by overlapping reads. So two genes found on one contig are physically joined: the assembler asserts their phase (which alleles travel together) without any statistics. Whether that assertion is right has to be checked (below). Genes on different contigs have no such link. The hap1/hap2 label of each contig is assigned separately, so "both on hap1" means nothing across contigs.

Step 2, placing contigs on the reference. The PAF file aligns each contig to GRCh38. One line per aligned block, 12 fixed columns:

contig       len      q.start  q.end    strand chrom len        t.start   t.end     match   block   MAPQ tags
h1tg000012l  1830551  10234    1811002  +      chr6  170805979  29501234  31301876  1795001 1801233 60   tp:A:P ...

This says that most of contig 12 covers chr6:29.50–31.30 Mb (class I) at 99.7% identity (match / block). The pipeline uses these lines to cut each haplotype down to the MHC (chr6:29.5–33.5 Mb, ±100 kb). Each cut piece is named contig:start-end, for example h1tg000012l:10234-1811002.

Step 3, finding the genes. Immuannot searches each cut piece for HLA genes and writes a GTF annotation, one line per feature:

h1tg000012l:10234-1811002  Immuannot  gene  412880  416121  .  +  .  gene_id "HLA-A"; allele "A*02:01:01:01"; ...

Step 4, Table 1. Each GTF gene becomes one row of Table 1: person, hap, contig (the cut-piece name above), gene, copy, allele call, gene_start/gene_end (relative to the cut piece, not to GRCh38), and quality fields. Two genes are "on the same contig" when their rows for the same person and haplotype carry the same contig value. That is a simple text comparison. Script 50 counts it for every gene pair over all haplotypes where both genes were called (50_qc_foundation/same_contig_matrix.tsv).

The rate falls with distance, because every extra stretch is a chance for the contig to end. Contigs end where the two parental copies are identical for longer than a read (the assembler cannot tell them apart), in segmental duplications (the class I region between A and B is full of HLA pseudogenes and repeats), or where coverage happens to be thin.

What it does not mean. "Same contig" means physically joined by the assembler. It does not guarantee that the join is correct. The trio check (Part 2) found that on A~B contigs the two genes came from different parents in about 41% of cases, so the assembler switched parents inside those contigs. B~C and the class II pairs had low wrong-parent rates (below 7.7%). Rules for using phased haplotypes follow from both numbers: the same contig, and a pair the trio check validates.

RNA-seq: how a blood sample becomes a gene expression number

What is in the tube. A cell's RNA is mostly not messenger RNA. By mass, ribosomal RNA (rRNA, the structural RNA of ribosomes) is about 80–85% of total RNA, transfer RNA (tRNA, the short adaptors that carry amino acids) about 10–15%, and messenger RNA (mRNA, the copies of genes that get translated) only about 1–5% (BioNumbers 111540). Blood adds one more problem: red-cell precursors fill it with globin mRNA (HBA1, HBA2, HBB), which can take a large share of reads (tens of percent) if it is not removed (Sci Rep 2020). Sequencing everything would spend most reads on rRNA and globin.

A worked TPM example. Gene X (2 kb) gets 400 reads and gene Y (10 kb) gets 1,000. Per kb that is 200 and 100. If all genes together give 1,000,000 per-kb units in this sample, X has 200 TPM and Y has 100 TPM. Y had more reads but fewer transcripts, because each Y transcript is five times longer and so yields more fragments. TPM is a share: if globin takes a large part of a sample, every other gene's TPM is pushed down a little.

The All of Us release (CDR v9; from the All of Us data documentation in reference/ and the RNA-seq metadata):

  • 8,980 whole-blood samples. 8,327 of these people also have long reads.
  • Library: Watchmaker RNA library prep with Polaris depletion. Abundant RNAs are removed with probes instead of selecting poly-A tails, so non-polyadenylated RNA, and some intronic reads from unspliced RNA, remain.
  • Paired-end short reads, about 80–600 million reads aligned in pairs (about 40–300 million pairs) per sample. The metadata records alignment with DRAGEN 4.2.4. The documentation also describes STAR alignment, so the exact aligner is stated inconsistently in the documentation.
  • Quantification: RNA-SeQC 2 (gene TPM, used by our script 55) and RSEM (gene and transcript TPM and expected counts). Only BAMs and these matrices are released, not raw FASTQ.

What this means for HLA and KIR. Gene-level TPM pools the two alleles of a gene and is computed against the reference genome, where HLA reads from divergent alleles can map poorly. Script 53 instead builds each person's own HLA sequences from their assembly and maps that person's RNA reads to them. That gives expression per allele, which is how allele-specific expression is measured (Part 7).

What is actually in the All of Us libraries (script 68). How to read "share of TPM". TPM shares are not the same as shares of reads: TPM divides by gene length, so short genes such as mitochondrial tRNAs get a larger share than their reads, and long genes a smaller one. The read-based numbers (rows 1–3) answer "what fraction of sequencing went where"; the TPM rows answer "what fraction of transcripts were this". So, for the question "what share of the reads are rRNA, tRNA or normal RNA": in these libraries about 0.5% of bases are rRNA (from ~80% in the tube), tRNA is essentially absent (see below), about 0.4% is globin, and the rest is RNA from genes: roughly 57% from exons, which is what expression is measured on, and 33% from introns of the same genes.

tRNA. Mature tRNAs are 70–90 bases long, shorter than the fragments kept during library prep, so they are almost absent from standard RNA-seq whatever the cell contains. The mitochondrial tRNAs annotated in the gene matrix are a small trace. Measuring tRNA needs special small-RNA protocols.
